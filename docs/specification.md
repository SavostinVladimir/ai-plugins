# Agent Frameworks: implementation specification

## Goal and scope
A reusable repository of independently installable agent workflows. Deliver the initial spec-review package, its existing five role prompts, native Codex files, and a dependency-free Python 3.11+ CLI. Do not install into the current user's live harness automatically. Preserve the destination project's .idea directory. The CLI has no client-selection flag; old target="codex" instance entries remain accepted for compatibility, other targets are rejected. Keep the existing Codex state binding and default state path stable so previously installed Codex packages can still be updated. No remote repository has been selected; prepare a local Git repository without publishing or committing on behalf of the user.

## Requirements
R1. Codex only. A package contains skills/<name>/SKILL.md and optional UI/assets, plus instructions.md and a small manifest. Native agents/*.toml are optional; a skill-only package has an empty models object in its plan. Native agent files are the source of truth, not generated from neutral prompts. Import the existing five role files and skill without weakening their review instructions. Keep models directly inside agent TOML. No adapters, shared-role compiler or separate profiles directory.
R2. Each agent declares its model and model_reasoning_effort directly (current five: gpt-6-luna, high). Optional per-role instance overrides and CLI --model/--effort may override fields on installation and are remembered for updates. No model environment variables. Paths can use CODEX_HOME or explicit overrides. No API calls or model fallback during installation; report runtime verification limitations.
R3. CLI commands: list, plan, install, update, status, uninstall, check. Select a package by ID. update --installed updates only packages recorded for this instance. Updates use the local checkout; users git pull --ff-only beforehand or check out a release tag for a pinned version. No implicit network activity.
R4. A TOML machine configuration supports named instances. Each instance is Codex-only, with separate agents, skills, instructions, config and state paths, and optional role overrides. CLI overrides take precedence over instance settings and remembered overrides, then native source defaults. Environment hints apply only to paths (CODEX_HOME), not models. TOML rather than previously illustrated YAML keeps the installer on Python standard library only. Explicit --config selects the machine config. Relative machine-config paths resolve against that file, not the caller's cwd. Explicit path flags resolve against cwd. Expand home and environment variables; reject unresolved variables. Never assume a custom directory is discovered by a corporate harness.
R5. Defaults: Codex agents in CODEX_HOME/agents and personal skills in HOME/.agents/skills, instructions in active CODEX_HOME/AGENTS.override.md if present, otherwise AGENTS.md. Codex home is CODEX_HOME or HOME/.codex. Explicit paths override these. config path is diagnostic: do not rewrite native config or permissions.
R6. Bind each state registry to its instance target and destination paths. Record package version, rendered-content digest, installed file hashes and pre-install originals. Preserve local model overrides by resolving the same instance on updates; warn rather than discard manual edits to generated files. Plan shows resolved paths, models, intended operations and conflicts without creating files. Resolve symlinked parent directories, refuse symlink final files, reject destination collisions and invalid package IDs/source traversal.
R7. Preflight all selected packages before a write. Refuse differing unowned files unless --adopt is explicitly supplied; preserve originals for uninstall. Identical unowned files may be adopted without changing their contents and must be restored on uninstall. Detect edits to managed files and managed instruction blocks; never overwrite them silently. Instructions are merged in one named block per package, preserving all surrounding text. Handle active Codex override. For preexisting legacy spec-review instructions, report that --adopt covers files but an existing unmarked automatic rule must be reconciled manually; do not create a duplicate automatically. No automatic full-file AGENTS replacement.
R8. Lock state for mutations, use atomic writes, retain a backup of pre-operation state and affected files, and roll back if a write fails. Detect changed destination contents again immediately before committing to reduce races. Do not hide permission failures or choose a different directory silently. Uninstall removes only unchanged owned artifacts and its own instruction block, restores originals, preserves unrelated files; state and recovery backups remain available. Runtime backups/state are not committed to source control.
R9. Installed skill uses actual installed role paths, Codex invocation and fresh-context instructions. Use fork_turns=none when supported. All five get the same version and original intent, never author reasoning or other first-round findings. Run waves under slot limits; missing tools/models/sources produce incomplete review. Standalone review is read-only. Preserve CUJ and grounding criteria, two-round limit, and meaningful final results. UI display_name must match the skill name exactly.
R10. Automatic rule goes in target-appropriate global instructions. Respect explicit user skips. The manager does not validate whether a corporate client loads arbitrary paths: check inspects filesystem/payload integrity and reports runtime discovery, model access and clean-context support as not verified. Live Codex model access is not claimed without a client test.
R11. Include README, corporate-path and new-framework documentation, example instance and native agent settings, tests using temporary directories, negative cases for conflicts and rollback, and portable specification. No secrets, usernames or source-machine absolute paths in shipped configuration.

## CUJ
J1 Install: user clones repository, runs list, selects spec-review, runs plan, inspects concrete paths/models/conflicts, then install. Sees installed paths and explicit runtime-verification limitations; skill becomes usable after the host loads it.
J2 Corporate setup: user copies the example machine file outside Git, enters mounted destination paths and a local model override, runs plan/install with --config and --instance. Output uses only those destinations; read-only mounts produce a concrete failure without a false success or alternate installation.
J3 Update: user pulls repository changes, runs status, then update spec-review or update --installed. Only selected/already installed packages are updated. A manual edit produces a conflict before mutation. Local instance model choices remain applied. CLI completion names each updated package/version and reports whether files changed.
J4 Review: user invokes $spec-review in Codex with original request and draft. Sees five role results or clearly incomplete checks; independent histories are required. Goal is a specification whose issues and evidence the user can inspect.
J5 Remove: user runs uninstall spec-review, sees a plan for managed files/block, then removal restores originals and leaves other instructions untouched. Modified managed artifacts cause a conflict. Successful completion explicitly names the removed package and confirms that original files/instructions were restored or unrelated content preserved.

## Acceptance
- Automated CLI and unit tests cover Codex rendering, parsing of generated TOML, command lifecycle, custom per-component paths, precedence, relative paths, override, multiple packages via a temporary fixture, update --installed, local role settings, idempotence, conflicts, adoption/restoration, unknown instances, bad paths, state binding, concurrent lock, transaction rollback, and instruction preservation.
- Installed skills reference shipped role paths and contain no accidental opposite-client commands. CUJ reviewer and skill-name UI labels exist in the installed output.
- Run a staged Codex installation under a temporary root and check/status/uninstall. Live account/model discovery and a real Codex session are separate, explicitly unverified integration checks.
- Existing global installation is unchanged. Destination code and docs are reviewable locally; no push or remote publication.
