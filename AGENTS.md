# О репозитории

Набор полезных навыков (skills), ролей субагентов и инструментов для harness Codex.
Сейчас доступны пакеты `spec-review` (пять ревьюеров спецификации), `code-review`
(семь ревьюеров кода), `session-review` (три роли разбора сессий) и
`code-review-journal` (журнал замечаний без ролей).
Python CLI выборочно устанавливает и обновляет пакеты из
локального checkout. Он не запускает модели и не настраивает сам harness.

## Карта файлов

- `frameworks/<id>/` — самостоятельный устанавливаемый пакет:
  - `manifest.toml` — идентификатор, версия, название и описание;
  - `agents/*.toml` — нативные роли Codex с промптами и параметрами модели;
  - `skills/<id>/SKILL.md` — условия запуска и сценарий работы навыка;
  - `skills/<id>/agents/openai.yaml` — метаданные навыка для интерфейса;
  - `instructions.md` — короткое правило автоматического запуска;
  - `tests/` — сценарии и фикстуры для проверки поведения ревьюеров.
- `manage.py` — точка входа CLI; `manager/cli.py` — аргументы и команды.
- `manager/configuration.py` — пути, экземпляры установки и валидация настроек.
- `manager/render.py` — обнаружение пакетов и подготовка устанавливаемых файлов.
- `manager/engine.py` — планирование и выполнение операций установки.
- `manager/state.py` — registry, хеши, управляемые блоки, блокировки и восстановление.
- `tests/` — автоматические тесты установщика, отдельно от фикстур навыков.
- `examples/` — примеры локальных настроек экземпляров и overrides.
- `docs/` — детали: `adding-frameworks.md`, `installation.md`,
  `corporate-environments.md`, `codex-home.md`; `specification.md` — спецификация менеджера.
- `README.md` — пользовательские команды и обзор возможностей.

## Как создавать и менять навыки и роли

Используй существующий пакет как образец; подробности — в `docs/adding-frameworks.md`.
Источник истины — файлы в `frameworks/`, а не их установленные копии.

1. Создай `frameworks/<id>/manifest.toml` с полями `id`, `version`, `name`,
   `description`. `id` совпадает с именем каталога и соответствует `[a-z][a-z0-9-]*`.
2. Если нужны роли, добавь `agents/<role>.toml`: `name` совпадает с именем файла без расширения;
   укажи `description`, `model`, `developer_instructions` и при необходимости
   `model_reasoning_effort`. Имена ролей должны быть уникальны между пакетами:
   все они устанавливаются в общий каталог `agents/`.
3. Добавь `skills/<id>/SKILL.md` с YAML front matter (`name`, `description`) и
   инструкциями. Установщик требует одноимённый навык; пакет может не иметь ролей.
   В `SKILL.md` маркер `{{agents_path}}` заменяется фактическим путём установки ролей;
   остальные файлы навыка копируются без преобразования.
4. Добавь `instructions.md`: `{{invocation}}` заменится на `$<id>`. Правило попадёт
   в управляемый блок глобальных инструкций, а не заменит файл целиком.
5. Добавь или обнови сценарии и ожидания в `frameworks/<id>/tests/`.
   Ожидаемые замечания предназначены координатору; независимым ревьюерам их не передают.
6. При выпуске изменений подними версию в manifest и обнови затронутую документацию.

Промпт и модель роли редактируются непосредственно в TOML. Общего компилятора
промптов и профилей моделей нет. В текущих review-пакетах роли используют
`gpt-6-luna`, effort `high` и независимый контекст `fork_turns="none"`;
координация и состав входных данных описаны в соответствующем `SKILL.md`.

## Как работает установщик

Требуется Python 3.11+, используются только стандартные библиотеки.
Команды: `list`, `plan`, `install`, `update`, `status`, `check`, `uninstall`.

- Пакеты обнаруживаются по `frameworks/*/manifest.toml`; отдельного списка регистрации нет.
- `plan` и `--dry-run` не создают файлов. `update` берёт исходники из checkout,
  без сетевого обновления. `update --installed` не устанавливает новые пакеты.
- `--codex-home` задаёт общий корень: `agents/`, `skills/`, глобальные инструкции
  и `.agent-frameworks/state/<instance>/`. При наличии `AGENTS.override.md`
  выбирается он, иначе `AGENTS.md`. Нативный `config.toml` менеджер не изменяет.
- Без `--codex-home`: роли и инструкции идут в `CODEX_HOME` (по умолчанию
  `~/.codex`), навыки — в `~/.agents/skills`, state — в
  `~/.agent-frameworks/state/codex/<instance>/`.
- Приоритет путей: явные флаги компонентов, затем `instance.paths`, затем значения
  общего корня/defaults. Пути из TOML считаются от его каталога, CLI-пути — от cwd.
  `--config` — настройки менеджера; `--config-path` — путь нативного конфига Codex.
- Модель/effort: CLI, затем настройки роли экземпляра, сохранённые overrides,
  исходный TOML. Явные overrides сохраняются для обновлений; `--reset-overrides`
  сбрасывает сохранённые, `--effort default` убирает поле effort.
- Registry отслеживает управляемые файлы и блоки. Чужие файлы и ручные изменения
  вызывают конфликт до записи, код выхода `2`. `--adopt` разрешает принять чужой
  payload с резервной копией, но не обходит конфликт ручных изменений.
- Сохраняй защиту от коллизий путей, небезопасных symlink, потери чужих инструкций
  и перезаписи нативного конфига. Ошибки записи откатываются; для аварий есть журналы.

## Проверки и границы изменений

Для изменений менеджера запускай:

```bash
python3 -m unittest discover -s tests -v
```

Тесты изолированы временными каталогами и не вызывают модели. Для изменения пакета
проверь `list`, `plan` и цикл `install / check / update / uninstall` с одним и тем же
`--codex-home` в отдельном временном каталоге. Не используй рабочие настройки
пользователя для проверки установщика.

`check` проверяет установленные файлы, а не доступность модели и качество ревью.
Изменения промптов требуют отдельной проверки реального запуска в Codex;
фикстуры в `frameworks/*/tests/` не исполняются автоматически через unittest.
Указывай, если live-проверка не выполнена.

Сохраняй существующее разделение модулей и формат соседних файлов. Для исправлений
менеджера добавляй целевой unittest. Не добавляй зависимости без необходимости.
Новые и изменённые рукописные комментарии пиши по-русски; сохраняй синтаксис
директив, метаданных и шаблонных маркеров. Локальные пути и настройки машины держи
вне Git. Не меняй установленные навыки, роли и глобальные инструкции без задачи
на установку или обновление.

## Наблюдаемые соглашения Python

- Имена функций и переменных — `snake_case`; классы тестов — `PascalCase` с суффиксом `Tests`, методы тестов — `test_<условие>`. Примеры: `manager/render.py` (`source_file`), `tests/test_codex_home.py` (`CommonRootTests`) и `tests/test_manager.py` (`test_plan_has_no_side_effects`).
- Проверки написаны на стандартном `unittest`: сценарии сгруппированы в `unittest.TestCase`, общая подготовка находится в `setUp`, временные каталоги очищаются через `addCleanup`. Для изоляции используются `tempfile.TemporaryDirectory`, `unittest.mock.patch` и `subTest`; см. `tests/test_manager.py` и `tests/test_codex_home.py`.
- В Python-файлах встречаются импорты стандартной библиотеки и локальных модулей `manager`. Группировка и порядок не вполне единообразны (`manager/cli.py`, `manager/render.py`, `tests/test_manager.py`), поэтому не вводи отдельного требования к сортировке импортов.
- Форматирование существующего кода неоднородно: различаются пробелы вокруг `=`, стиль строк и плотность записей (например, `manager/cli.py` и `manager/render.py`). Сохраняй стиль ближайшего кода; не трактуй эти различия как обязательный формат и не переформатируй несвязанные строки.
